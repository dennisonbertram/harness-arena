# GLM Fast provider stream failure A/B

**Investigation date:** 2026-07-31
**Status:** confirmed Wafer context-sensitive failure; upstream-versus-adapter
boundary still open

## Result

The failing turn was first replayed with the same six-message body once with
the gateway pinned to Wafer and once with the gateway pinned to Fireworks.
That A/B showed a provider differential. A second set of Wafer-only replays
then used the exact resolved system prompt from the public run, the exact
`bash`, `read`, `edit`, and `write` schemas generated by the installed Pi
runtime, and the historical user/assistant/tool-result sequence. These calls
also made no Pi/provider retry attempt.

| Replay | HTTP result | Stream result | Gateway evidence |
|---|---|---|---|
| Historical control | Pi recorded `stopReason: "error"`, `errorMessage: "terminated"` | — | Historical response IDs: `gen_01KYTDDH06X7KT5T53FV6H14WJ`, `gen_01KYTDDHSRQ5QM2Z68A2DERJB9`, `gen_01KYTDFMK3JRAV06WTRZK8MCB1` |
| Wafer | `200`, `text/event-stream` | **0 body bytes for 90 seconds; no first byte, finish event, or response ID** | `x-vercel-id: fra1::fra1::d5xt7-1785451761659-08cfff9e48e6` |
| Fireworks | `200`, `text/event-stream` | **23,592 bytes in 17 chunks; first byte at `2026-07-30T22:50:52.288Z`; maximum idle gap 82 ms** | Response ID `gen_01KYTKJBYMKJZDSKD884K9KT2V`; `x-vercel-id: fra1::fra1::qthp5-1785451761717-119aa700aaf1` |

The exact-input Wafer controls sharpened the result:

| Exact-input variant | Result |
|---|---|
| Full context, `stream: true` | HTTP `200`, zero body bytes, client timeout after 90 seconds |
| Remove only the final tool result, `stream: true` | HTTP `200`, 5,728 bytes in 3 chunks, maximum idle gap 130 ms; response ID `gen_01KYTN39HMW5ZN5CEXFET00JQB` |
| Keep the tool-call history but omit tool definitions, `stream: true` | HTTP `200`, 1,527,239 bytes in 328 chunks, then timeout; this changed the request into an invalid/ambiguous tool context and did not finish cleanly |
| Full context, `stream: false` | No response was received before the 90-second timeout |

The Wafer call therefore opened successfully at the HTTP layer but stalled
before emitting a response body. Fireworks streamed the same request to
completion. The client-side Wafer result was:

```text
TimeoutError: The operation was aborted due to timeout
```

## Conclusion

This isolates the failure to the **Wafer route or the gateway's Wafer
adapter**, and the exact-input controls show that the final tool-result
context is part of the trigger. Removing only that result converts the silent
stall into a normal Wafer stream.

It is not only a generic SSE framing failure: the full exact request also
stalls with `stream: false`. The same proxy, request shape, response mode, and
client completed normally with Fireworks in the earlier A/B.

The experiment does not distinguish between a Wafer upstream that accepted
the request and never produced output, and a gateway-side Wafer integration
that failed before forwarding output. That boundary requires gateway/provider
logs or an equivalent direct Wafer comparison.

The historical `terminated` label should be read as the downstream agent's
normalization of an interrupted response-body read, not as evidence that the
provider returned a normal HTTP error. In the replay, Wafer returned headers
with HTTP 200 and then produced no body bytes.

The no-tool-definition variant is not a clean success control. It leaves
assistant tool calls and tool results in the history while removing the
definitions needed to interpret them, and Wafer emitted a very large stream
without completing. Its useful conclusion is only that removing tool
definitions changes the failure mode; it cannot be compared to a valid agent
conversation.

## Telemetry captured

The temporary sidecar instrumentation now records:

- request correlation ID, model, requested/pinned provider, and request size;
- response status and sanitized headers;
- first-byte time;
- every response chunk timestamp and size, total bytes, and maximum idle gap;
- response/finish ID when present;
- disconnects and serialized stream/body-read errors, including causes.

The runner carries the sidecar correlation summary into the task event log.
See [`gateway-proxy.mjs`](../scripts/runner/gateway-proxy.mjs) and
[`runner.mjs`](../scripts/runner/runner.mjs).

## Reproduction notes and limits

- The exact replay used the public run
  `35fbb4fd-406b-496d-8e59-fcd6e242d0d6`, task
  `model-extraction-relu-logits`, whose stored resolved system prompt is 3,020
  characters. The historical failing turn contains one user message, one
  assistant message with two tool calls, and two tool results.
- The session JSONL does not store the wire-level tool schema, so the four
  schemas were generated from the installed Pi runtime that produced the run.
  The exact prompt and message content came from the public run record and
  trace.
- The direct exact-input calls were run with the same one-shot client and
  90-second timeout. They were approved for this investigation and were not a
  production benchmark run.
- The local sidecar initially copied the incoming `content-length` after
  injecting the provider pin, causing undici to reject the transformed body
  with `UND_ERR_INVALID_ARG: invalid content-length header`. It now removes
  transport framing headers and lets `fetch` derive them. An exact,
  production-shaped Fireworks replay through the fixed sidecar completed with
  HTTP `200`, 2,120 response bytes in 4 chunks, response ID
  `gen_01KYTNVTP0V9RSXGHJEH1M2C5A`, and 37.081 seconds total time.
- The Vercel request IDs above identify the gateway requests. They do not by
  themselves expose the provider's internal failure cause.

## Follow-up

The production Wafer competition is retired rather than silently changing its
provider. New competition runs use a separate Fireworks-versioned competition
with `providerOptions.gateway.only: ["fireworks"]`; there is no fallback route
between the two leaderboards.

Any further Wafer investigation should be an isolated diagnostic replay, not a
production competition entry. Preserve the correlation ID, `x-vercel-id`,
first-byte/idle timings, and exact stream error together. The next external
evidence needed is the gateway/provider-side explanation for why this
tool-result context makes Wafer return `200 text/event-stream` without a body,
while the shortened context succeeds.
